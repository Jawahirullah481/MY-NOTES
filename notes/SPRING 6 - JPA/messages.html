📖 Chapter 1 - Why Hibernate Came Into Existence
━━━━━━━━━━━━━━━━━━

🔹 The Problem

Suppose we are building an Employee Management System.

We create an Employee object in Java.

Employee emp = new Employee();

This object lives only in memory.

When the application stops, the object disappears.

Businesses cannot afford to lose data whenever the application restarts.

Therefore, application data must be stored permanently.

This is called Persistence.

👉 Persistence = Storing data permanently in a database.

━━━━━━━━━━━━━━━━━━

🔹 How Java Applications Stored Data Before Hibernate

Traditionally, Java applications used JDBC.

Flow:

Java Application
↓
JDBC
↓
Database


JDBC allows Java applications to execute SQL queries and interact with the database.

━━━━━━━━━━━━━━━━━━

🔹 Problem 1 - Too Much Boilerplate Code

For every database operation we write:

• Connection creation
• SQL query creation
• PreparedStatement handling
• ResultSet handling
• Exception handling
• Resource closing

The same code gets repeated everywhere.

Result:

❌ More code
❌ More bugs
❌ Harder maintenance

━━━━━━━━━━━━━━━━━━

🔹 Problem 2 - Manual Mapping

Database returns rows.

Example:

id = 1
name = John
salary = 50000


Java works with objects.

So developers manually convert database rows into Java objects.

Employee
↓
id = 1
name = John
salary = 50000


This conversion process is called Mapping.

Developers had to write this mapping code repeatedly.

━━━━━━━━━━━━━━━━━━

🔹 Problem 3 - SQL Everywhere

Business logic and SQL become mixed together.

Service Layer
↓
SQL Query
↓
Business Logic
↓
SQL Query


Result:

❌ Difficult to maintain
❌ Difficult to read
❌ Difficult to modify

━━━━━━━━━━━━━━━━━━

🔹 Problem 4 - Database Dependency

Suppose the application uses PostgreSQL today.

Later the company decides to migrate to Oracle.

Some SQL queries may require modification.

Application becomes tightly coupled to a specific database.

━━━━━━━━━━━━━━━━━━

🔹 Problem 5 - Object Relational Impedance Mismatch

This is the biggest problem.

Java understands:

• Objects
• Classes
• Inheritance
• Relationships

Database understands:

• Tables
• Rows
• Columns
• Foreign Keys

Example:

Java World

Employee
Department
Address


Database World

EMPLOYEE Table
DEPARTMENT Table
ADDRESS Table


Both worlds represent data differently.

This difference is called:

👉 Object Relational Impedance Mismatch

━━━━━━━━━━━━━━━━━━

🔹 The Big Question

Developers started asking:

"Why should we manually convert objects into rows and rows into objects?"

"Why can't a framework do this automatically?"

━━━━━━━━━━━━━━━━━━

🔹 Birth of ORM

ORM stands for:

Object Relational Mapping

ORM acts as a bridge between:

Java Objects
↕️
Database Tables


Its job is to automatically convert:

Object → Row

and

Row → Object

━━━━━━━━━━━━━━━━━━

🔹 Hibernate

Hibernate is a popular ORM framework for Java.

Instead of manually handling mapping and SQL operations, Hibernate performs most of the work automatically.

Goal of Hibernate:

• Reduce boilerplate code
• Simplify database operations
• Automatically map objects and tables
• Improve developer productivity

━━━━━━━━━━━━━━━━━━

📝 Summary

• Data must be stored permanently → Persistence

• JDBC was traditionally used for database operations

• JDBC introduced lots of repetitive code

• Developers manually mapped rows and objects

• Java Objects and Database Tables are fundamentally different

• This difference is called Object Relational Impedance Mismatch

• ORM was introduced to solve this problem

• Hibernate is a Java ORM framework

📖 Chapter 2 - Hibernate Architecture

━━━━━━━━━━━━━━━━━━

🔹 Where We Left Off

In the previous chapter, we learned that JDBC had several problems:

• Too much boilerplate code

• Manual mapping between rows and objects

• SQL scattered throughout the application

• Object Relational Impedance Mismatch

To solve these problems, ORM was introduced.

One of the most popular ORM frameworks is Hibernate.

Now the question is:

❓How does Hibernate actually communicate with the database?

━━━━━━━━━━━━━━━━━━

🔹 High-Level Architecture

Hibernate sits between the application and the database.

Flow:

Application

↓

Hibernate

↓

JDBC

↓

Database

Notice something important.

Hibernate does NOT replace JDBC.

Hibernate internally uses JDBC.

Hibernate simply makes JDBC easier to use.

🔹 Main Components of Hibernate

Hibernate revolves around three important components:

• SessionFactory

• Session

• Transaction

Think of them as:

Factory → Worker → Safety Mechanism

Let's understand them one by one.

━━━━━━━━━━━━━━━━━━

🔹 SessionFactory

Suppose a company wants to manufacture cars.

Would it build a new factory every time a customer orders a car?

No.

The factory is created once.

Cars are produced many times.

SessionFactory works similarly.

It is a heavyweight object responsible for creating Session objects.

Application Startup

↓

Create SessionFactory

↓

Use it throughout the application's lifetime


Typically, only one SessionFactory is created per database.

━━━━━━━━━━━━━━━━━━

🔹 Why SessionFactory Is Expensive

When SessionFactory starts, Hibernate:

• Reads configuration files

• Reads entity classes

• Creates metadata

• Prepares SQL mappings

• Initializes caches

All this work takes time and memory.

Therefore:

✅ Create once

❌ Create repeatedly

Creating SessionFactory for every request is a common beginner mistake.

━━━━━━━━━━━━━━━━━━

🔹 Session

Session is the most important object in Hibernate.

It represents a connection between your application and Hibernate.

Whenever you want to:

• Save data

• Update data

• Delete data

• Read data

You use a Session.

Flow:

SessionFactory

↓

creates

↓

Session

━━━━━━━━━━━━━━━━━━

🔹 Real-Life Analogy

Imagine a bank.

The bank building is SessionFactory.

A customer entering the bank and performing operations is Session.

Many customers can visit the same bank.

Similarly:

One SessionFactory

↓

Many Sessions

━━━━━━━━━━━━━━━━━━

🔹 What Can Session Do?

Session provides methods such as:

• save()

• persist()

• update()

• merge()

• delete()

• get()

• load()

Almost every Hibernate operation happens through Session.

━━━━━━━━━━━━━━━━━━

🔹 Transaction

Now imagine a money transfer.

Step 1:

Deduct ₹10,000 from Account A.

Step 2:

Add ₹10,000 to Account B.

What happens if the application crashes after Step 1?

Money is deducted.

Money is not credited.

The database becomes inconsistent.

This is the problem transactions solve.

━━━━━━━━━━━━━━━━━━

🔹 Purpose of Transaction

A transaction ensures:

Either all operations succeed

OR

All operations fail

Nothing in between.

Example:

Begin Transaction

↓

Update Account A

↓

Update Account B

↓

Commit Transaction


If something goes wrong:

Begin Transaction

↓

Update Account A

↓

Error

↓

Rollback Transaction

Its primary responsibility is:

📖 Chapter 3 - Entity Mapping and the @Entity Annotation

━━━━━━━━━━━━━━━━━━

🔹 Where We Left Off

In the previous chapter, we learned that Hibernate uses:

• SessionFactory

• Session

• Transaction

to communicate with the database.

Now a new question arises.

Suppose we have a Java class:

Employee

How does Hibernate know:

• Should this become a database table?

• Should its fields become columns?

• Should it even be stored in the database?

Hibernate cannot guess these things automatically.

We need a way to tell Hibernate about our intentions.

━━━━━━━━━━━━━━━━━━

🔹 The Need for Mapping

Remember the core purpose of Hibernate.

Java World

↓

Hibernate

↓

Database World


Hibernate's main job is converting:

Object ↔️ Table

For this conversion to happen, Hibernate needs mapping information.

It needs answers to questions like:

• Which class maps to which table?

• Which field maps to which column?

• Which field is the primary key?

Without this information Hibernate is blind.

━━━━━━━━━━━━━━━━━━

🔹 What Is Entity Mapping?

Entity Mapping is the process of connecting:

Java Class

↓

Database Table


Once mapping is configured, Hibernate automatically handles conversions.

Example:

Employee Object

↓

EMPLOYEE Table Row


and vice versa.

━━━━━━━━━━━━━━━━━━

🔹 Enter @Entity

The first annotation Hibernate needs is:

@Entity

This annotation tells Hibernate:

👉 "This class should be treated as a database entity."


In simple terms:

@Entity means:

"Please create a relationship between this class and a database table."


━━━━━━━━━━━━━━━━━━

🔹 Example

Suppose we have:

Employee

with fields:

• id

• name

• salary

When Hibernate sees @Entity, it understands:

Employee is no longer just a normal Java class.

It now represents data that can be stored in a database.

━━━━━━━━━━━━━━━━━━

🔹 What Happens Without @Entity?

Suppose we create:

Employee

Customer

Department

Product

Inventory

Hibernate sees all these classes.

How does it know which ones should be stored?

It doesn't.

Without @Entity, Hibernate ignores the class.

No mapping is created.

No table is generated.

No persistence happens.

━━━━━━━━━━━━━━━━━━

🔹 Entity vs Normal Class

Normal Java Class

• Exists only in memory

• Hibernate ignores it

• No database mapping

Entity Class

• Managed by Hibernate

• Can be persisted

• Mapped to a table

• Participates in ORM

━━━━━━━━━━━━━━━━━━

🔹 Real-Life Analogy

Imagine a school.

Thousands of people enter the campus daily.

Students

Teachers

Visitors

Workers

Security Guards

Now suppose the administration wants to maintain student records.

How will they identify students?

By assigning a Student ID.

Similarly, Hibernate identifies persistent classes using @Entity.

It marks them as special classes that need database management.

━━━━━━━━━━━━━━━━━━

🔹 Entity Naming

By default, Hibernate uses:

Class Name

↓

Table Name

Example:

↓

EMPLOYEE (or employee depending on database settings)

↓

↓

━━━━━━━━━━━━━━━━━━

🔹 Rules for an Entity Class

A good entity class should:

• Have @Entity annotation

• Have a primary key

• Have a no-argument constructor

• Be a top-level class

• Not be final (recommended)

Don't worry about all these rules now.

We'll cover them one by one.

━━━━━━━━━━━━━━━━━━

🔹 Why Is Primary Key Important?

Imagine an Employee table containing:

Employee 1

Employee 2

Employee 3

Employee 4

How will Hibernate uniquely identify a specific employee?

It needs a unique identifier.

This leads to the concept of:

Primary Key

Every entity must have one.

🔹 A New Problem Appears

Now Hibernate knows:

✅ Which class should be persisted

But it still doesn't know:

❌ Which field uniquely identifies a row

Example:

Employee

• id

• name

• salary

Which field should be treated as the primary key?

📝 Summary

📖 Chapter 7 - Flush Mechanism and Dirty Checking Internals

━━━━━━━━━━━━━━━━━━

🔹 Where We Left Off

In the previous chapter, we learned:

• Persistence Context stores Persistent entities

• Hibernate tracks entity changes

• Dirty Checking automatically detects modifications

• First-Level Cache avoids unnecessary database queries

Now a very important question arises.

Suppose we modify an entity.

employee.setSalary(80000.0);


Will Hibernate immediately execute:

UPDATE employee
SET salary = 80000
WHERE id = 1;


No.

Hibernate usually delays SQL execution.

Why?

Because executing SQL is expensive.

This leads us to the concept of Flush.

━━━━━━━━━━━━━━━━━━

🔹 What Is Flush?

Flush means:

👉 Synchronizing Persistence Context with the Database.

Think of it as:

"Sending pending changes to the database."

Important:

Flush does NOT mean Commit.

Many beginners think both are the same.

They are not.

━━━━━━━━━━━━━━━━━━

🔹 Understanding With an Example

Suppose:

Employee employee =
session.get(Employee.class, 1L);

employee.setSalary(80000.0);


Current situation:

Persistence Context

↓

Salary = 80000

Database

↓

Salary = 50000

Notice:

Database is not yet updated.

Only the Persistence Context contains the latest value.

━━━━━━━━━━━━━━━━━━

🔹 Why Hibernate Delays SQL Execution

Imagine updating an employee 10 times.

employee.setSalary(60000);

employee.setSalary(65000);

employee.setSalary(70000);

employee.setSalary(80000);


If Hibernate executed UPDATE every time:

❌ 4 SQL statements

Instead Hibernate waits.

Final value:

80000

Then executes only one UPDATE.

This improves performance.

━━━━━━━━━━━━━━━━━━

🔹 What Happens During Flush?

Before Flush:

Persistence Context

↓

Salary = 80000

Database

↓

Salary = 50000

After Flush:

Persistence Context

↓

Salary = 80000

Database

↓

Salary = 80000

Now both are synchronized.

━━━━━━━━━━━━━━━━━━

🔹 Flush Does Not Commit

This is very important.

Suppose:

session.flush();


Hibernate executes SQL.

Database receives UPDATE.

But transaction is still open.

If rollback happens:

transaction.rollback();


Changes are undone.

Therefore:

Flush

≠

Commit

━━━━━━━━━━━━━━━━━━

🔹 Difference Between Flush and Commit

Flush:

• Executes SQL

• Synchronizes database and Persistence Context

• Transaction remains active

Commit:

• Flushes pending changes

• Permanently saves transaction

• Ends transaction

Think:

Flush = Send Changes

Commit = Finalize Changes

━━━━━━━━━━━━━━━━━━

"from Employee"
).list();

Reason:

Query should see the latest data.

🔹 What Is Cascading?

Cascading means:

👉 Propagating an operation from one entity to another.

Think:

Parent Entity

↓

Operation

↓

Child Entity

Example:

Department
    ↓
 Employees


If Department is saved,

Department

Employee is ignored.

Result:

🔹 Database Structure

Department

id | name

id | name | department_id

But Employee INSERT is not executed.

━━━━━━━━━━━━━━━━━━

• Cascading propagates operations from parent to child entities

• Without cascade, operations affect only the current entity

• CascadeType.PERSIST → Save children automatically

• CascadeType.REMOVE → Delete children automatically

• CascadeType.MERGE → Merge children automatically

• CascadeType.REFRESH → Refresh children automatically

• CascadeType.DETACH → Detach children automatically

• CascadeType.ALL → Applies all cascade operations

• Cascade does not create relationships

• Cascade only controls operation propagation

Example :

    cascade = CascadeType.ALL
)
private List<Employee> employees;

    @OneToMany

Hibernate sees:

Both sides appear to define the relationship.

Hibernate thinks:

Two relationships?

Because Hibernate doesn't know:

Which side should manage the relationship?

Which side controls the foreign key?

So Hibernate creates a bridge table.

This is usually not what we want.

Exactly what we wanted.

• One query loads parent entities

🔹 LazyInitializationException

One of Hibernate's most famous exceptions.

Code:

Session session =
sessionFactory.openSession();

Employee employee =
session.find(
    Employee.class,
    1L
);

session.close();


Later:

employee.getDepartment();


Exception:

LazyInitializationException


━━━━━━━━━━━━━━━━━━

🔹 Why?

Department wasn't loaded.

Session already closed.

Hibernate can't fetch it anymore.

━━━━━━━━━━━━━━━━━━

Option 1

JOIN FETCH


Best solution.

Access association before closing session.

employee.getDepartment()
        .getName();


Not preferred.

━━━━━━━━━━━━━━━━━━

Use EAGER.

📝 Summary

• Fetching decides when related data is loaded

• LAZY = Load when accessed

• EAGER = Load immediately

• OneToMany and ManyToMany are LAZY by default

• ManyToOne and OneToOne are EAGER by default

• LAZY helps performance

• LAZY can cause N+1 problem

• JOIN FETCH solves most N+1 problems

• LazyInitializationException occurs when lazy data is accessed after Session is closed

• Prefer LAZY + JOIN FETCH over EAGER
