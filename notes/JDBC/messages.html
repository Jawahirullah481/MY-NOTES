# 1. JDBC Architecture

JDBC (Java Database Connectivity) is an API that allows Java applications to communicate with databases.

### Architecture Flow

Java Application
      ↓
JDBC API (java.sql)
      ↓
DriverManager
      ↓
JDBC Driver
      ↓
Database


### Explanation

1. Java Application → Your program.
2. JDBC API → Interfaces like Connection, Statement, ResultSet.
3. DriverManager → Loads and manages database drivers.
4. JDBC Driver → Converts JDBC calls to DB-specific protocol.
5. Database → PostgreSQL, MySQL, Oracle, etc.

### JDBC Steps

1. Load driver
2. Create connection
3. Create statement
4. Execute query
5. Process results
6. Close resources

# 3. Simple JDBC Program

import java.sql.*;

public class Test {

  public static void main(String[] args) throws Exception {

    Class.forName("org.postgresql.Driver");

    Connection con = DriverManager.getConnection(
        "jdbc:postgresql://localhost:5432/test",
        "user",
        "password");

    Statement st = con.createStatement();

    ResultSet rs = st.executeQuery("SELECT * FROM employee");

    while(rs.next()) {
      System.out.println(
        rs.getInt("id") + " " +
        rs.getString("name"));
    }

    rs.close();
    st.close();
    con.close();
  }
}

# 12. Transaction Management in JDBC

### What is a Transaction?

A group of SQL operations executed as a single unit.

Example:

Transfer money

1. debit account
2. credit account

Both must succeed.

---

## setAutoCommit(false) (Important)

By default:

autoCommit = true


Each SQL query commits automatically.

Example:

UPDATE A → committed
UPDATE B → fails


Result → inconsistent data

---

### Disable Auto Commit

con.setAutoCommit(false);


Now we control commit manually.

---

### commit()

Saves all changes permanently.

con.commit();


---

### rollback()

Undo changes if error occurs.

con.rollback();


---

### Savepoint

Savepoint allows partial rollback.

Example:

Step1
Step2
SAVEPOINT
Step3
Step4
ERROR


Rollback to savepoint → Step1, Step2 kept.

---

### Example using all functions

Connection con = DriverManager.getConnection(url);

con.setAutoCommit(false);

try {

Statement st = con.createStatement();

st.executeUpdate("UPDATE acc SET bal=bal-100 WHERE id=1");

Savepoint sp = con.setSavepoint("sp1");

st.executeUpdate("UPDATE acc SET bal=bal+100 WHERE id=2");

con.commit();

}
catch(Exception e){

con.rollback();

}


Rollback to savepoint:

con.rollback(sp);


Release savepoint:

con.releaseSavepoint(sp);

# 14. ResultSet Types

ResultSet defines cursor movement capability.

---

## 1. TYPE_FORWARD_ONLY

Cursor moves only forward.

Row1 → Row2 → Row3


Example:

Statement st = con.createStatement(
ResultSet.TYPE_FORWARD_ONLY,
ResultSet.CONCUR_READ_ONLY);


Use case:

✔️ Large data reading
✔️ Best performance

---

## 2. TYPE_SCROLL_INSENSITIVE

Cursor can move forward and backward.

Changes in DB not visible.

Example:

Statement st = con.createStatement(
ResultSet.TYPE_SCROLL_INSENSITIVE,
ResultSet.CONCUR_READ_ONLY);

ResultSet rs = st.executeQuery("SELECT * FROM emp");

rs.last();
rs.previous();
rs.first();


---

## 3. TYPE_SCROLL_SENSITIVE

Cursor moves both directions and reflects DB changes.

Example:

Statement st = con.createStatement(
ResultSet.TYPE_SCROLL_SENSITIVE,
ResultSet.CONCUR_READ_ONLY);


---

# Concurrency Modes

| Mode             | Description        |
| ---------------- | ------------------ |
| CONCUR_READ_ONLY | cannot update rows |
| CONCUR_UPDATABLE | can update rows    |

---

### Example for CONCUR_UPDATABLE

Statement st = con.createStatement(
ResultSet.TYPE_SCROLL_SENSITIVE,
ResultSet.CONCUR_UPDATABLE);

ResultSet rs = st.executeQuery("SELECT * FROM emp");

rs.next();

rs.updateString("name","John");

rs.updateRow();

# Top 15 Tricky JDBC Interview Questions

---

# 1️⃣ Why is PreparedStatement faster than Statement?

Because PreparedStatement is precompiled by the database.

Flow:

Statement
Execute SQL → Parse → Compile → Execute
(repeated every time)


PreparedStatement
Parse → Compile → Execute
Execute
Execute
Execute


✔️ Parsing happens only once
✔️ Execution becomes faster

---

# 2️⃣ How does PreparedStatement prevent SQL Injection?

Because it separates SQL logic from user input.

Bad example:

String sql = "SELECT * FROM user WHERE name='"+name+"'";


User input:

' OR '1'='1


Query becomes:

SELECT * FROM user WHERE name='' OR '1'='1'


Now all rows are returned.

Safe version:

PreparedStatement ps =
con.prepareStatement(
"SELECT * FROM user WHERE name=?");

ps.setString(1,name);


Here input is treated only as data, not SQL.

---

Resources:

* Connection
* Statement
* ResultSet

If not closed:

✔️ Memory leaks
✔️ DB connections exhausted
✔️ Application crash

Best practice:

try-with-resources


Example:

    Statement st = con.createStatement()) {

}

# How Connection Pooling Works (Step by Step)

Suppose your pool configuration is:

maximumPoolSize = 20


So the pool maintains maximum 20 database connections.

---

# Scenario: 1000 Users Access Application

Important point:

Users ≠ Database Connections

A user request only needs a connection for a very short time.

Example request flow:

User request arrives
      ↓
Get connection from pool
      ↓
Execute query (few milliseconds)
      ↓
Return connection to pool


So connections are quickly reused.

---

# Timeline Example

Let’s assume 1000 users send requests.

But each query takes 20 ms.

### First moment

Pool: 20 connections
Users requesting: 1000


Pool gives connections to first 20 requests.

User1 → Conn1
User2 → Conn2
...
User20 → Conn20


---

### After query completes (~20 ms)

Connections are returned to the pool.

Conn1 released
Conn2 released
...
Conn20 released


Now next users get connections.

User21 → Conn1
User22 → Conn2
...


So connections are reused extremely fast.

---

# Important Behavior (Your Question)

You asked:

> only after existing using connections are completed, then only connection is allocated for other users?

✔️ Yes — but not exactly like a long wait.

What actually happens:

If pool is full:
    Request waits in queue


Example:

Pool size = 20
Active connections = 20
User21 request arrives


Then:

User21 waits until one connection is returned


But the wait is usually milliseconds.

---

        Application
             │
             ▼
        Connection Pool
     ┌───────────────────┐
     │ Conn1  Conn2 ...  │

Requests borrow connections like this:

# Important Concept

Connections are not per user.

They are per database operation.

Example:

User opens page:

HTTP request arrives
Service layer runs SQL
Connection used for 5–50 ms
Connection returned


So one connection may serve hundreds of users per second.

Database connections are heavy resources.

If 1000 connections open:

DB memory usage ↑
CPU usage ↑
Context switching ↑


Performance becomes worse.

That’s why:

Typical pool size = 10–30


Even for thousands of users.

# 1️⃣ Idle Connections

### What is an Idle Connection?

An idle connection is a connection that:

is created
but currently not being used


It is sitting in the pool waiting for a request.

---

### Example

Connection pool configuration:

Maximum connections = 20
Minimum idle = 5


When the application starts:

Pool creates 5 connections


These 5 connections are idle connections.

Pool
------------
C1 (idle)
C2 (idle)
C3 (idle)
C4 (idle)
C5 (idle)


---

### When a user request comes

User1 → takes C1
User2 → takes C2


Now pool becomes:

C1 (in use)
C2 (in use)
C3 (idle)
C4 (idle)
C5 (idle)


---

### Why Idle Connections Are Important

If no idle connections exist:

Application must create new DB connection


That takes time.

But with idle connections:

Request → instantly gets connection


So response becomes very fast.

---

# 2️⃣ Connection Timeout

### What is Connection Timeout?

It is the maximum time a user waits to get a connection from the pool.

If no connection becomes available within this time:

Exception is thrown


---

### Example

Pool configuration:

Maximum connections = 20
Connection timeout = 30 seconds


Scenario:

20 users already using connections
User21 requests connection


User21 waits.

If a connection is freed within:

30 seconds


User21 gets it.

If not:

SQLTransientConnectionException


Example error:

Connection is not available, request timed out after 30000ms


---

### Why Timeout Is Important

Without timeout:

users could wait forever


Timeout protects the system.

---

# 3️⃣ Connection Leak Detection

### What is a Connection Leak?

A connection leak happens when a developer forgets to close a connection.

Example mistake:

Connection con = dataSource.getConnection();

Statement st = con.createStatement();
ResultSet rs = st.executeQuery("select * from users");

// developer forgets con.close()


Now the connection:

never returns to the pool


This slowly exhausts all connections.

---

### Example Problem

Pool size:

20 connections


If 20 developers forget to close connections:

All connections stuck
New users cannot access database
Application crashes


---

### Leak Detection Solution

Modern pools like HikariCP detect leaks.

Example configuration:

leakDetectionThreshold = 2000ms


Meaning:

If a connection is not returned within 2 seconds
Pool prints warning


Example log:

Connection leak detected!
Connection held for 2500ms


---

# Correct Way to Avoid Leaks

Use try-with-resources.

try(Connection con = dataSource.getConnection();
    PreparedStatement ps = con.prepareStatement("select * from users");
    ResultSet rs = ps.executeQuery()) {

    while(rs.next()) {
        System.out.println(rs.getString(1));
    }
}


Now:

Connection automatically returned to pool

Calling con.close() in connection pooling and manual connection creation :

Manual Connection (using `DriverManager`)
con.close() physically closes the database connection, and a new connection must be created for the next request.

Connection Pool (using DataSource in Apache Tomcat)
con.close() does not close the actual DB connection; it returns the connection to the pool for reuse by other users.
