# SEURITY INTRODUCTION

When building a web application, one of the most critical concerns is security.

A secure system must ensure three fundamental principles:
| Principle       | Meaning                                           |
| --------------- | ------------------------------------------------- |
| Confidentiality | Only authorized users can access data             |
| Integrity       | Data cannot be modified illegally                 |
| Availability    | The system remains accessible to legitimate users |


Modern web applications achieve this by combining multiple technologies such as:

* password hashing
* authentication frameworks
* tokens
* encrypted communication

To understand why these mechanisms exist, we must first understand how authentication evolved over time.

---

# The Story of How a Secure Application Works 🔐

---

# 1. The Application Without Security

Imagine you built a simple API server.

It has endpoints like:

GET /users
GET /orders
DELETE /orders/10


Anyone on the internet can call these APIs.

A random person could run:

curl https://myapp.com/users


And boom 💥

They see all user data.

Even worse:

DELETE /orders/10


Someone could delete data.

So the first question the application asks is:

> Who are you?

This is where authentication comes in.

---

# 2. First Level of Protection — Login

A user tries to enter the system.

POST /login
username = jawa
password = ****


The server checks the database.

Is username correct?
Is password correct?


If correct:

User authenticated


But now another problem appears.

Every time the user makes a request, we cannot ask for the password again.

Example:

GET /orders
username = jawa
password = ****


Even though HTTPS encrypts it, sending passwords repeatedly is bad because:

* password may leak
* database must verify password every request
* system becomes slow

So developers invented a better mechanism.

---

# 3. Session-Based Authentication

Instead of sending passwords repeatedly:

1. User logs in once
2. Server verifies credentials
3. Server creates a session

Example session:

sessionId = A7G8H9K2


Server stores it:

sessionId → userId
A7G8H9K2     25


Server sends this session ID to the browser.

Usually via cookie:

Set-Cookie: SESSIONID=A7G8H9K2


Now every request automatically includes the session cookie.

GET /orders
Cookie: SESSIONID=A7G8H9K2


Server checks the session store and identifies the user.

This approach worked for many years.

---

# 4. Problems With Sessions

Sessions work well for small applications, but modern systems face several issues.

---

## Server Memory Problem

Sessions must be stored on the server.

1 user → 1 session
10,000 users → 10,000 sessions


This consumes memory.

Large systems may have millions of sessions.

---

## Load Balancer Problem

Modern applications run multiple servers.

        Load Balancer
             │
      ┌──────┴──────┐
   Server A      Server B


User logs in:

Server A creates session


Next request may go to Server B.

Server B cannot find session


User appears logged out.

Solutions like sticky sessions or shared session stores (Redis) are required.

But they increase complexity.

---

## Microservices Problem

Modern architectures often use microservices.

API Gateway
     │
 ┌───┴───┐
User   Order   Payment
Service Service Service


Session sharing across services becomes difficult.

---

## Stateful Server Problem

Sessions make servers stateful.

Meaning the server must remember client information.

Cloud-native systems prefer stateless services.

---

# 5. Token-Based Authentication

To solve session limitations, systems moved to token-based authentication.

Instead of storing sessions:

1. Server generates a token
2. Token contains user identity
3. Client sends token with each request

This token is commonly a JSON Web Token.

# 6. Password Security — Hashing

Before issuing tokens, the server must securely store passwords.

Storing plain passwords is dangerous.

Bad example:

username | password
jawa     | mypassword


If the database leaks, all passwords are exposed.

Instead, passwords are hashed using bcrypt.

Example:

mypassword
↓
$2a$10$E9N5x8b...93kdjS


Database stores:

username | password_hash
jawa     | $2a$10$E9N5x8b...93kdjS


During login:

1. User enters password
2. bcrypt hashes it
3. Hash is compared

bcrypt protects stored passwords.

---

# 7. The Temporary Identity Card — JWT

After login, the server creates a temporary identity card.

This card is the JWT token.

Example payload:

{
  userId: 25,
  role: "USER",
  exp: 1712345678
}


The token is digitally signed:

signature = hash(header + payload + secretKey)


The token structure:

HEADER.PAYLOAD.SIGNATURE


The client receives the token.

---

# 8. Using the Token for Requests

Instead of sending passwords, the client sends the token.

GET /orders
Authorization: Bearer <JWT>


Server validation process:

1. Decode token
2. Recalculate signature
3. Compare signatures

If valid:

User authenticated


No database lookup required.

This is called stateless authentication.

---

# 9. Preventing Token Tampering

Suppose a hacker modifies the token.

Original payload:

role = USER


Hacker changes it:

role = ADMIN


But the signature was created using:

hash(header + payload + secretKey)


When payload changes:

signature becomes invalid


Server rejects the request.

The attacker cannot recreate the signature without the secret key.

---

# 10. Why Token Expiration Exists

If a token is stolen, the attacker could use it.

To limit this risk, tokens include expiration.

Example:

exp = 1712345678


When time exceeds this value:

Token expired
Access denied


After the token is expired, hacker cannot access the application with the same token.

---

# 11. Access Token and Refresh Token

Modern systems improve this using two tokens.

### Access Token

Short lifetime.

10–15 minutes


Used for API calls.

---

### Refresh Token

Long lifetime.

7–30 days


Used only to generate new access tokens.

Flow:

Login
   ↓
Access Token (15 min)
Refresh Token (7 days)


When access token expires:

Client sends refresh token
Server generates new access token


---

# 12. The Invisible Protector — HTTPS

All communication occurs over HTTPS.

HTTPS uses Transport Layer Security encryption.

Without HTTPS:

username
password
JWT


can be intercepted.

With HTTPS:

All data is encrypted


Attackers only see encrypted traffic.

---

# 13. Third-Party Login — OAuth2

Sometimes users don't want to create new accounts.

They prefer:

* Login with Google
* Login with GitHub
* Login with Facebook

This is handled by OAuth 2.0.

OAuth2 allows applications to delegate authentication to trusted providers.

Flow:

User clicks "Login with Google"
↓
Redirect to Google
↓
Google authenticates user
↓
Google sends authorization code
↓
Application receives user identity


Often after OAuth login, the application still creates a JWT.

---

# 14. Where Spring Security Fits

The system uses Spring Security to enforce security rules.

Spring Security handles:

1. Login authentication
2. Password verification
3. JWT validation
4. Role-based access control


Example rules:

/admin/** → ADMIN only
/user/** → USER allowed

# 15. Complete Security Architecture

The final system works like this:

User
 ↓
Login (username/password)
 ↓
bcrypt verifies password
 ↓
JWT token generated
 ↓
Client stores token
 ↓
Client sends token in requests
 ↓
Spring Security validates token
 ↓
Authorization check
 ↓

 ↓
Database accessed


All communication occurs over HTTPS.

---

# Final Mental Model

Modern application security is layered.

HTTPS → encrypts network communication
bcrypt → protects stored passwords
JWT → represents authenticated user
Signature → prevents token modification
Expiration → limits token misuse
OAuth2 → enables third-party login
Spring Security → enforces authentication and authorization


Together these mechanisms ensure:

Only the right user
can access the right resource
for the right amount of time

# 2️⃣ Customizing SecurityFilterChain

Disable default login form and configure endpoints.

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {

        http
            .csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers("/auth/**").permitAll()
                    .anyRequest().authenticated()
            )
            .sessionManagement(session ->
                    session.sessionCreationPolicy(SessionCreationPolicy.STATELESS)
            );

        return http.build();
    }
}

# 3️⃣ Custom UserDetailsService (Load User From DB)

@Service
public class CustomUserDetailsService implements UserDetailsService {

    @Autowired
    private UserRepository userRepository;

    @Override
    public UserDetails loadUserByUsername(String username)
            throws UsernameNotFoundException {

        User user = userRepository.findByUsername(username)
                .orElseThrow(() ->
                        new UsernameNotFoundException("User not found"));

        return new org.springframework.security.core.userdetails.User(
                user.getUsername(),
                user.getPassword(),
                List.of(new SimpleGrantedAuthority("ROLE_USER"))
        );
    }
}

@Component
public class JwtService {

    private final String SECRET_KEY = "mysecretkeymysecretkeymysecretkey";

    public String generateToken(String username) {

        return Jwts.builder()
                .setSubject(username)
                .setIssuedAt(new Date())
                .setExpiration(
                        new Date(System.currentTimeMillis() + 1000*60*60)
                )
                .signWith(getSigningKey(), SignatureAlgorithm.HS256)
                .compact();
    }

    private Key getSigningKey() {

        byte[] keyBytes = SECRET_KEY.getBytes();

        return Keys.hmacShaKeyFor(keyBytes);
    }
}

# 8️⃣ JWT Filter (Parsing Token For Every Request)

Custom filter extending OncePerRequestFilter.

@Component
public class JwtAuthFilter extends OncePerRequestFilter {

    @Autowired
    private JwtService jwtService;

    @Autowired
    private CustomUserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain)
            throws ServletException, IOException {

        String authHeader = request.getHeader("Authorization");

        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            filterChain.doFilter(request, response);
            return;
        }

        String token = authHeader.substring(7);

        String username = jwtService.extractUsername(token);

        if (username != null &&
            SecurityContextHolder.getContext().getAuthentication() == null) {

            UserDetails userDetails =
                    userDetailsService.loadUserByUsername(username);

            UsernamePasswordAuthenticationToken authToken =
                    new UsernamePasswordAuthenticationToken(
                            userDetails,
                            null,
                            userDetails.getAuthorities()
                    );

            SecurityContextHolder.getContext()
                    .setAuthentication(authToken);
        }

        filterChain.doFilter(request, response);
    }
}

# 9️⃣ Register JWT Filter in SecurityFilterChain

@Bean
public SecurityFilterChain filterChain(
        HttpSecurity http,
        JwtAuthFilter jwtAuthFilter) throws Exception {

    http
        .csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/**").permitAll()
                .anyRequest().authenticated()
        )
        .sessionManagement(session ->
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS)
        )
        .addFilterBefore(
                jwtAuthFilter,
                UsernamePasswordAuthenticationFilter.class
        );

    return http.build();
}

In Spring Security, SecurityContextHolder is the central place where the currently authenticated user's security information is stored and accessed during a request.

Below is the brief but clear understanding.

---

# 1️⃣ What is SecurityContextHolder?

SecurityContextHolder is a static utility class that holds a SecurityContext.

SecurityContextHolder
        ↓
   SecurityContext
        ↓
   Authentication
        ↓
   UserDetails (principal)


Example access:

Authentication authentication =
        SecurityContextHolder.getContext().getAuthentication();

String username = authentication.getName();


---

# 2️⃣ What Does It Store?

It stores an Authentication object.

Example:

UsernamePasswordAuthenticationToken


Inside it:

Authentication
 ├── principal → UserDetails
 ├── credentials → password
 ├── authorities → roles
 └── authenticated → true/false


Example structure:

Authentication
   principal : User(username=john)
   authorities : ROLE_USER
   authenticated : true


---

# 3️⃣ Why Do We Store Authentication Here?

Because any part of the application may need to know who the current user is.

Example places:

* Controllers
* Services
* Method security (@PreAuthorize)
* Auditing
* Logging

Example:

String username =
SecurityContextHolder
    .getContext()
    .getAuthentication()
    .getName();


This works anywhere in the request flow.

---

# 4️⃣ Who Sets It?

During authentication.

Example inside a JWT filter:

UsernamePasswordAuthenticationToken authToken =
        new UsernamePasswordAuthenticationToken(
                userDetails,
                null,
                userDetails.getAuthorities()
        );

SecurityContextHolder
        .getContext()
        .setAuthentication(authToken);


Once set, Spring considers the user authenticated for the rest of the request.

---

# 5️⃣ Is It Per Request?

Yes.

By default Spring Security uses:

ThreadLocal


Internally:

SecurityContextHolderStrategy
        ↓
ThreadLocal<SecurityContext>


Since each HTTP request is handled by a separate thread, the authentication becomes request-scoped automatically.

Example:

Request 1 → Thread 21 → SecurityContext A
Request 2 → Thread 34 → SecurityContext B


So user data never mixes between requests.

---

# 6️⃣ Lifetime of SecurityContext

It depends on the security configuration.

### Session Based Authentication

(Default Spring Security)

User logs in
↓
Authentication stored in session
↓
SecurityContext restored for each request
↓
Valid until session expires


---

### JWT / Stateless Authentication

When using JWT:

Request comes with JWT
↓
JWT filter validates token
↓
Authentication stored in SecurityContextHolder
↓
Used during request
↓
Cleared after request completes


Lifetime:

Only during that request


Next request:

JWT parsed again


---

# 7️⃣ How It Gets Cleared

At the end of each request, Spring Security clears it.

Handled by filter:

SecurityContextHolderFilter


Flow:

Request start
   ↓
SecurityContext created
   ↓
Authentication set
   ↓
Request processed
   ↓
SecurityContext cleared


---

# 8️⃣ Internal Working

Default strategy:

MODE_THREADLOCAL


Other options exist:

| Mode | Description |
| --------------------------- | ----------------------------- |
| MODE_THREADLOCAL | default |
| MODE_INHERITABLETHREADLOCAL | child threads inherit context |
| MODE_GLOBAL | one global context |

But almost always ThreadLocal is used.

01:49
SecurityContextHolder is a Spring Security utility that stores the current user's Authentication object inside a SecurityContext. It uses ThreadLocal so each request thread maintains its own authenticated user details. During authentication, Spring sets the Authentication in the SecurityContextHolder, and it remains available throughout the request lifecycle and is cleared after the request completes.
