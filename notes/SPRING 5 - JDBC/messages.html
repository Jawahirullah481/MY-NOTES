# 1️⃣ Why Spring JDBC Exists

Before Spring JDBC, we used plain JDBC.

Example (traditional JDBC):

Connection con = DriverManager.getConnection(url, user, pass);

PreparedStatement ps =
        con.prepareStatement("select * from users where id=?");

ps.setInt(1, 1);

ResultSet rs = ps.executeQuery();

while(rs.next()){
    System.out.println(rs.getString("name"));
}

rs.close();
ps.close();
con.close();


Problems:

* too much boilerplate
* resource closing
* exception handling
* repetitive code

Spring introduced JdbcTemplate to solve this.

# 7️⃣ RowMapper (ResultSet → Object)

public class UserRowMapper implements RowMapper<User> {

    @Override
    public User mapRow(ResultSet rs, int rowNum)
            throws SQLException {

        User user = new User();

        user.setId(rs.getInt("id"));
        user.setName(rs.getString("name"));
        user.setEmail(rs.getString("email"));

        return user;
    }
}

# 🔟 NamedParameterJdbcTemplate

Instead of ?, we use named parameters.

@Autowired
private NamedParameterJdbcTemplate namedJdbcTemplate;


Example:

public User findByEmail(String email){

    String sql =
    "select * from users where email=:email";

    MapSqlParameterSource params =
            new MapSqlParameterSource();

    params.addValue("email", email);

    return namedJdbcTemplate.queryForObject(
            sql,
            params,
            new UserRowMapper()
    );
}


Advantages:

* readable queries
* avoids parameter order mistakes

# 1️⃣1️⃣ Batch Insert

public void saveUsers(List<User> users){

    String sql =
    "insert into users(name,email) values (?,?)";

    jdbcTemplate.batchUpdate(
        sql,
        users,
        users.size(),
        (ps,user)->{
            ps.setString(1,user.getName());
            ps.setString(2,user.getEmail());
        }
    );
}

# The Story of How @Transactional Works in Spring

## 1️⃣ The Problem Without Transactions

Imagine a banking system.

A user transfers money.

Process:

Transfer ₹1000
     ↓
Debit Account A
     ↓
Credit Account B


If something fails after debiting:

Account A → debited ❌
Account B → not credited ❌


Now the database becomes inconsistent.

To solve this, databases support transactions.

A transaction ensures:

All operations succeed
OR
All operations rollback


---

# 2️⃣ Enter @Transactional

Spring provides the annotation:

@Transactional


This tells Spring:

Start a transaction
Execute all operations
Commit if successful
Rollback if failure


Example:

@Service
public class BankService {

    @Transactional
    public void transfer(Long fromId, Long toId, double amount){

        accountRepository.debit(fromId, amount);

        accountRepository.credit(toId, amount);

    }
}


Execution flow:

Transaction starts
      ↓
debit()
      ↓
credit()
      ↓
commit


If an exception occurs:

Transaction starts
      ↓
debit()
      ↓
credit() fails
      ↓
rollback


---

# 3️⃣ Where @Transactional Is Usually Placed

Best practice:

Controller
    ↓
Service  (@Transactional here)
    ↓
Repository
    ↓
Database


Example:

@Service
@Transactional
public class OrderService {

    public void placeOrder(){
        saveOrder();
        updateInventory();
    }

}


All methods inside run in the same transaction.

---

# 4️⃣ What Happens When Service Calls Repository

Example:

@Transactional
public void placeOrder(){

    orderRepository.saveOrder();

    orderRepository.updateInventory();
}


Execution flow:

Transaction begins
      ↓
saveOrder()
      ↓
updateInventory()
      ↓
commit


Both SQL operations use one database connection.

If second query fails:

rollback entire transaction


So:

saveOrder() is also rolled back


---

# 5️⃣ Service Calling Another Service

Example:

@Service
public class PaymentService {

    @Autowired
    private AccountService accountService;

    @Transactional
    public void processPayment(){

        accountService.debit();

        accountService.credit();
    }
}


Second service:

@Service
public class AccountService {

    public void debit(){}

    public void credit(){}

}


Execution flow:

processPayment()
     ↓
Transaction starts
     ↓
debit()
     ↓
credit()
     ↓
commit


Both run in the same transaction.

Reason:

Default propagation = REQUIRED


Meaning:

Join existing transaction


---

# 6️⃣ When Called Service Also Has @Transactional

Example:

@Service
public class AccountService {

    @Transactional
    public void debit(){}

    @Transactional
    public void credit(){}

}


Execution still remains:

processPayment()
     ↓
Transaction starts
     ↓
debit() joins same transaction
     ↓
credit() joins same transaction
     ↓
commit


Because propagation:

REQUIRED


---

# 7️⃣ Creating a New Transaction

Sometimes we want a separate transaction.

Example:

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void debit(){}


Now flow becomes:

processPayment() → Transaction T1
        ↓
debit() → Transaction T2
        ↓
T2 commits
        ↓
processPayment continues


Two transactions exist:

T1 and T2


---

# 8️⃣ Important Rule – Spring Bean Only

Transactions work only when Spring manages the object.

✔️ Works:

@Autowired
AccountService accountService;


❌ Doesn't work:

AccountService service = new AccountService();


Reason:

Spring cannot apply transaction proxy


---

# 9️⃣ Self Invocation Problem

Example:

@Service
public class PaymentService {

    public void processPayment(){

        validate();

        performPayment();
    }

    @Transactional
    public void performPayment(){}
}


Execution:

processPayment()
      ↓
performPayment()


But transaction does NOT start.

Reason:

Internal method call bypasses Spring proxy


---

# 🔟 How @Transactional Actually Works

Spring uses AOP (Aspect Oriented Programming).

Spring creates a proxy object.

Execution flow:
00:16 
Controller
     ↓
Spring Proxy
     ↓
Transaction Interceptor
     ↓
Begin Transaction
     ↓
Actual Service Method
     ↓
Commit / Rollback


The component responsible is:

PlatformTransactionManager


For JDBC applications:

DataSourceTransactionManager

# 1️⃣1️⃣ What Happens Internally with JDBC

When transaction starts:

Connection created
     ↓
Bound to current thread


Spring stores connection in ThreadLocal.

Now every repository call uses:

Same connection


Flow:

Transaction begins
      ↓
Connection assigned to thread
      ↓
Repository query
      ↓
Repository query
      ↓
Commit / Rollback


---

# 1️⃣2️⃣ Rollback Rules

Default rollback occurs for:

RuntimeException
Error


Example:

@Transactional
public void transfer(){

    debit();

    throw new RuntimeException();
}


Result:

rollback


---

Checked exceptions do not rollback.

Example:

throw new Exception();


Solution:

@Transactional(rollbackFor = Exception.class)


---

# 1️⃣3️⃣ Transaction Propagation

Propagation defines how transactions interact.

Common ones:

| Propagation | Behavior |
| ------------- | --------------------------- |
| REQUIRED | Join existing or create new |
| REQUIRES_NEW | Always create new |
| SUPPORTS | Use if exists |
| NOT_SUPPORTED | Run without transaction |

Default:

REQUIRED


---

# 1️⃣4️⃣ Isolation Levels

Isolation defines visibility of uncommitted data.

Example:

@Transactional(isolation = Isolation.READ_COMMITTED)


Common levels:

READ_UNCOMMITTED
READ_COMMITTED
REPEATABLE_READ
SERIALIZABLE

# 1️⃣5️⃣ Complete Flow of Transactional Request

Client Request
      ↓
Controller
      ↓
Service (@Transactional)
      ↓
Spring Proxy
      ↓
Transaction Manager
      ↓
Begin Transaction
      ↓

      ↓

      ↓
Commit / Rollback
      ↓
Response returned

# Final Understanding

@Transactional ensures:

Multiple database operations behave as one unit of work.


Spring achieves this by:

AOP Proxy
Transaction Manager
Thread-bound JDBC connection


---

# Short Interview Answer

@Transactional is a Spring annotation used for declarative transaction management. It works through Spring AOP proxies that intercept method calls, start a database transaction before method execution, and commit or roll back the transaction depending on the outcome of the method execution.

# ✅ Case 1 — Transaction Works

@Service
public class TestService {
  
  @Transactional
  public void test1() {
    test2();
  }
  
  private void test2() {
    // DB operations
  }
}


### What happens

External call → test1()
      ↓
Spring Proxy intercepts
      ↓
Transaction STARTS
      ↓
test2() is called internally
      ↓
Runs inside SAME transaction
      ↓
Commit / Rollback


✔️ Transaction is active
✔️ test2() runs inside transaction

---

# ❌ Case 2 — Transaction DOES NOT Work

@Service
public class TestService {
  
  private void test1() {
    test2();
  }
  
  @Transactional
  public void test2() {
    // DB operations
  }
}


### What happens

If test1() is called from outside:

External call → test1()
      ↓
NO proxy interception
      ↓
test2() is called internally
      ↓
@Transactional is IGNORED ❌


Even though test2() has @Transactional, it won’t work.

---

# 🚨 Root Cause (Very Important)

In Spring Framework, transactions work using:

AOP Proxy


### Rule:

@Transactional works ONLY when method is called THROUGH Spring proxy


---

# 🔥 Key Concept (Must Remember)

| Scenario | Transaction? |
| --------------------------------------- | ------------ |
| External call → @Transactional method | ✅ YES |
| Internal method call (same class) | ❌ NO |
| Private method with @Transactional | ❌ NO |

---

# ⚠️ Extra Important Point

Even if you do:

@Transactional
private void test2() {}


It still won’t work because:

Private methods cannot be proxied


---

# ✅ How to Fix Case 2

Move method to another service.

@Service
public class TestService {
  
  @Autowired
  private AnotherService anotherService;

  public void test1() {
    anotherService.test2();
  }
}


@Service
public class AnotherService {

  @Transactional
  public void test2() {
    // works
  }
}


Now:

External → TestService → AnotherService (via proxy) → Transaction works ✅


---

# 🧠 Final One-Line Rule

> @Transactional works only when the method is public and called through a Spring proxy (i.e., from another bean or external call).
If we call it manually or if it private method, then @Transactional won't work
