# ❓ 1. Problems Docker Solves

Before Docker, developers often faced the problem:

> "It works on my machine, but not on yours."

### 🤔 Why?

Different systems may have different:

* Operating Systems
* Library versions
* Runtime versions
* Environment variables
* Installed software
* Configurations

### 🖥 Example

Developer Machine

Java 21
Maven 3.9
MySQL 8


Production Server

Java 17
Maven 3.6
MySQL 5.7


### ⚠️ Result

Application may fail even though the code is correct.

### ✅ Docker Solution

Docker packages everything required to run the application into a Container.

> Build Once → Run Anywhere

════════════════════════════════════

# 🖥 2. Physical Servers

A Physical Server is an actual computer that runs applications directly on its Operating System.

### 🏗 Architecture

Hardware
   │
Operating System
   │
Application 1
Application 2
Application 3


### ❌ Problems

* Applications share the same OS.
* Dependency conflicts can occur.
* One application's crash may affect others.
* Difficult to isolate applications.
* Poor resource utilization.
* Scaling requires purchasing more hardware.

════════════════════════════════════

# 💻 3. Virtual Machines (VM)

A Virtual Machine (VM) is a software-based computer that runs its own Operating System.

### 🏗 Architecture

Hardware
   │
Hypervisor
   │
VM 1      VM 2      VM 3
 │          │         │
Guest OS  Guest OS  Guest OS
 │          │         │
Apps       Apps      Apps


### ✅ Advantages

* Strong isolation
* Multiple Operating Systems on one machine
* Better resource utilization than Physical Servers

### ❌ Limitations

* Every VM needs its own Guest OS.
* Consumes more RAM and CPU.
* Larger storage usage.
* Slow startup (minutes).

### 💡 Memory Trick

> VM = A complete computer inside another computer.

════════════════════════════════════

# 📦 4. Containers

A Container is a lightweight package that contains:

* Application
* Libraries
* Dependencies
* Runtime
* Configuration

Unlike a VM, a Container does not include a full Operating System.

### 🏗 Architecture

Hardware
   │
Host OS
   │
Docker Engine
   │
Container 1
Container 2
Container 3


Each container is isolated from others but shares the Host OS Kernel.

### 💡 Memory Trick

> Container = Application + Everything Required to Run It

# ⚖️ 5. Physical Server vs VM vs Container

| Feature        | Physical Server | Virtual Machine        | Container       |
| -------------- | --------------- | ---------------------- | --------------- |
| OS             | One OS          | Each VM has its own OS | Shares Host OS  |
| Startup        | Minutes         | Minutes                | Seconds         |
| Size           | Large           | Large                  | Small           |
| Resource Usage | High            | Medium-High            | Low             |
| Isolation      | Low             | High                   | High (OS-Level) |
| Portability    | Difficult       | Moderate               | Excellent       |


### 🎯 Quick Summary

* Physical Server → One OS, Many Applications
* Virtual Machine → Many Operating Systems on one Machine
* Container → Many Isolated Applications sharing one Host OS

Docker is an open-source platform used to build, package, ship, and run applications using Containers.

Instead of installing an application and its dependencies manually on every machine, Docker packages everything into a Container.

# 🔍 10. How Docker Works Internally

Let's understand what happens when we execute:

docker run nginx


### Execution Flow

1. Docker Client receives the command.
2. Client sends the request to Docker Daemon.
3. Daemon searches for the Image locally.
4. If Image doesn't exist, Docker automatically performs:

docker pull nginx


5. Image is stored locally.
6. Container is created.
7. Docker adds a Writable Layer on top of the Image.
8. Container starts running.

### 💡 Important Point

> Images are Read-Only.
>
> Every Container gets its own Writable Layer.

# ❓ 1. What is an Image?

A Docker Image is a read-only blueprint used to create Containers.

It contains everything required to run an application:

* Application Code
* Runtime
* Libraries
* Dependencies
* Configuration Files

### 🏠 Think of it like

* House Blueprint → Image
* Built House → Container

or

* Coffee Recipe → Image
* Prepared Coffee → Container

### 💡 Remember

> Image = Template / Blueprint
> Container = Running Instance

════════════════════════════════════

# 🧱 2. Image Layers

A Docker Image is not a single file.

It consists of multiple layers, where each instruction in a Dockerfile creates a new layer.

### 🖥 Example Dockerfile

FROM ubuntu
RUN apt update
RUN apt install nginx
COPY app/ /app
CMD ["nginx", "-g", "daemon off;"]


### 📚 Layers Created

Layer 5 → CMD
Layer 4 → COPY
Layer 3 → RUN apt install nginx
Layer 2 → RUN apt update
Layer 1 → FROM ubuntu


Each layer is stored separately and reused whenever possible.

### 💡 Memory Trick

> One Dockerfile Instruction = One Image Layer

════════════════════════════════════

# 🔒 3. Read-only Layers

All Image layers are Read-Only.

Once an Image is built:

* Existing layers cannot be modified.
* Docker creates a new layer instead.

### 🖥 Example

Ubuntu Base
      ↓
Java Installed
      ↓
Application Copied


These layers remain unchanged.

If the application changes, Docker creates a new Application Layer while reusing all previous layers.

 Image
────────
Layer 3
Layer 2
Layer 1


### 💡 Remember

> Images never change. Docker always creates a new layer.

════════════════════════════════════

# ✏️ 4. Writable Layer

Since Images are Read-Only, Docker adds a Writable Layer when a Container starts.

Container Writable Layer
──────────────-──────-─
Image Read-only Layer 3
Image Read-only Layer 2
Image Read-only Layer 1


All runtime changes happen here:

* Creating files
* Editing files
* Installing packages
* Writing logs
* Temporary data

The original Image never changes.

### 🤔 Why do we need a Writable Layer?

Applications often need to:

* Create log files
* Save uploaded files
* Generate reports
* Store temporary files

If Image layers were modified directly:

❌ Every Container would affect the original Image.

Instead, Docker stores all changes in the Writable Layer.

### 💡 Golden Rule

> Image = Read-Only
> Container = Read + Write

════════════════════════════════════

# 🗂 5. Union File System (UnionFS)

Docker combines multiple Image layers into a single virtual filesystem using UnionFS.

Although an Image has many layers, the Container sees only one filesystem.

### 🖥 Example

Layer 3
Layer 2
Layer 1
────────────
Container View


The application never knows multiple layers exist.

It simply sees normal files and folders.

### 📝 Example

Image contains:

Layer 1

/etc/os-release


Layer 2

/usr/bin/java


Layer 3

/app/app.jar


Writable Layer

/app/log.txt


The Container sees:

/
├── app
│   ├── app.jar
│   └── log.txt
├── etc
│   └── os-release
└── usr
    └── bin
        └── java


### 🔄 What Happens When You Modify a File?

Suppose:

config.txt exists in a Read-Only Image layer.

When you modify it inside the Container:

1. Docker copies the file to the Writable Layer.
2. The modified version is stored there.
3. UnionFS shows the modified file to the application.

This is called Copy-on-Write (CoW).

### ✅ Benefits

* Saves storage
* Faster downloads
* Layer reuse
* Efficient image sharing

### 💡 Memory Trick

> UnionFS = Many Layers → One Filesystem

════════════════════════════════════

# ⚡️ 6. Layer Caching

Docker caches Image layers during the build process.

If a layer hasn't changed, Docker reuses it instead of rebuilding it.

### 🖥 Example

FROM ubuntu
RUN apt update
RUN apt install nginx
COPY app/ /app


Suppose only your application code changes.

Docker reuses:

* FROM ubuntu ✅
* RUN apt update ✅
* RUN apt install nginx ✅

Only this layer is rebuilt:

COPY app/ /app


### 💡 Benefit

Builds become much faster because unchanged layers are reused.

# 2. Build Context

## 📖 What is Build Context?

When you run:

docker build .


Docker sends the entire current directory to the Docker Daemon.

This directory is called the Build Context.

Example:

project/
│
├── Dockerfile
├── app.jar
├── config.yml
├── README.md
└── src/


All these files become available during the build.

### 💡 Why is it Important?

Because COPY and ADD can access only files inside the Build Context.

Example:

COPY app.jar /app/


Docker copies app.jar from the Build Context.

If the file is outside the Build Context:

❌ COPY ../app.jar /app


Docker throws an error.

Docker stores these layers separately.

* Efficient storage
* Layer caching

# 5. Layer Caching

Docker caches every successfully built layer.

Example:

FROM ubuntu
RUN apt update
RUN apt install nginx
COPY app /app


### First Build

FROM      ✅ Build
RUN       ✅ Build
RUN       ✅ Build
COPY      ✅ Build


### Second Build (Only App Changed)

FROM      ✅ Cached
RUN       ✅ Cached
RUN       ✅ Cached
COPY      🔄 Rebuilt


Only the changed layer is rebuilt.

Result: Builds become much faster.

# 6. Cache Invalidation

Docker rebuilds a layer if:

* The instruction changes.
* A copied file changes.
* Any previous layer changes.

Example:

Original:

RUN apt install nginx


Modified:

RUN apt install apache2


Result:

This layer
      ↓
Rebuilt

Every layer after it
      ↓
Also rebuilt


### ⚠️ Important Rule

If one layer changes:

> That layer and every layer after it must also be rebuilt.

### 💡 Good Practice

Keep frequently changing files near the end.

Example:

FROM ubuntu

RUN apt update

RUN apt install openjdk

COPY app.jar .


Since the application changes frequently, only the last layer is rebuilt.
